## Issues and discussions

- The repository currently indexed as the upstream project is `Zackriya-Solutions/meetily` (not `Gi99lin/meetily`); its repository description explicitly advertises speaker diarization and the `sortformer` topic, so upstream has now shipped a first-party implementation rather than merely discussing it: https://github.com/Zackriya-Solutions/meetily
- Open issue #659 proposes an *alternative* integrated backend, MOSS-Transcribe-Diarize, while explicitly describing the existing Whisper/Parakeet + diarization pipeline as already available and worth retaining. It calls for MOSS to be optional/experimental and warns that performance, VRAM, speed, and quality need benchmarking: https://github.com/Zackriya-Solutions/meetily/issues/659
- The public documentation now describes speaker diarization as beta and says it works for recordings, imports, and retranscriptions: https://docs.meetily.ai/
- The current product documentation says the Speakers action appears only after results exist, and instructs users to enable Speaker Diarization **before processing** or retranscribe with it enabled. This is direct precedent for making diarization a persisted processing preference rather than a separate post-hoc button click: https://docs.meetily.ai/features/meeting-workspace
- In the v0.0.4 release discussion, the older issue “Identify Attendees Based on Voice” (#56) appeared under planned backend improvements / future roadmap, showing that the project historically separated *voice identity* from basic diarization. The current docs likewise distinguish adding/correcting labels from automatically knowing a person's identity: https://github.com/Zackriya-Solutions/meetily/discussions/88
- A search of the public Discussions index did not surface a dedicated diarization design thread; relevant design evidence is mainly in repository history, issues, and shipped documentation: https://github.com/Zackriya-Solutions/meetily/discussions
- Source-level correction: upstream Community `main` does **not** contain a Sortformer/ONNX multi-speaker module. Its README still says diarization/identification is planned for PRO, while the only substantial implementation on Community `main` is the older whisper.cpp server's stereo-channel energy attribution and optional TinyDiarize speaker-turn detection: https://github.com/Zackriya-Solutions/meetily/blob/main/README.md and https://github.com/Zackriya-Solutions/meetily/blob/main/backend/whisper-custom/server/server.cpp
- Issue #56 (opened 2025-03-21) specifically asks for detecting speakers, matching them to known attendees, and labeling transcripts, suggesting pyannote-whisper. It remains open, unassigned, has no maintainer response, and has no linked branch/PR. This is strong evidence that upstream has not completed known-attendee voice identification in Community Edition: https://github.com/Zackriya-Solutions/meetily/issues/56
- GitHub's repository issue search for “diarization” surfaces open requests for VibeVoice-ASR (#335) and remote ASR (#527), plus a cluster of closed spam/duplicate FunASR proposals (#482, #486–#491). #486 was explicitly closed “not planned,” but its spam context means this is not a general maintainer rejection of diarization: https://github.com/Zackriya-Solutions/meetily/issues?q=is%3Aissue%20diarization
- Issue #335 proposes VibeVoice as an optional single-pass ASR+diarization backend. Crucially, it calls the 7B model compute/VRAM-heavy and slower than TDT models, recommending asynchronous post-meeting processing rather than realtime captions. The issue is open, unassigned, and has no linked development: https://github.com/Zackriya-Solutions/meetily/issues/335
- Issue #486 proposed replacing separate Whisper/Parakeet + diarization with FunASR/SenseVoice/CAM++, but was marked `[SPAM]` and closed “not planned” with no discussion or linked work. Treat it as a rejected submission, not a technical evaluation of CAM++ or integrated diarization: https://github.com/Zackriya-Solutions/meetily/issues/486
- Issue #519 asks to disable realtime transcription; its appearance in the diarization search and the shipped post-processing mode reinforces that users care about separating resource-heavy stages: https://github.com/Zackriya-Solutions/meetily/issues/519
- #519 gives the concrete rationale: limited-hardware machines slow down during realtime ASR, while post-recording Whisper Turbo is preferred for performance/reliability. Its acceptance criteria preserve the choice and persist it across sessions; it does **not** argue for always-on concurrent background inference: https://github.com/Zackriya-Solutions/meetily/issues/519

## Maintainer direction and constraints

- Public positioning remains local/private processing; this strongly favors an on-device model and makes cloud diarization unsuitable as an unconditional default: https://github.com/Zackriya-Solutions/meetily
- The v0.3.0 release introduced an explicit post-processing mode: disable live transcription during a meeting and process the entire recording afterward when accuracy matters more than realtime output. That is upstream precedent for making heavy analysis a post-recording job rather than running it concurrently with live ASR: https://github.com/Zackriya-Solutions/meetily/releases/tag/v0.3.0
- Public messaging has been inconsistent over time: one indexed branch/page says speaker diarization was planned as a PRO feature, while the current repository and docs advertise a beta diarization implementation. We should reuse code that is actually present under the repository license, but avoid assuming every advertised PRO workflow is in Community Edition: https://github.com/Zackriya-Solutions/meetily?ref=curatifyai
- There is no recorded maintainer endorsement or rejection on issue #56; silence plus no linked development means we cannot infer an approved Community architecture from that issue: https://github.com/Zackriya-Solutions/meetily/issues/56
- Product docs reveal the intended job ordering: retranscription first saves the replacement transcript, then starts speaker identification. Cancellation during the latter can leave the new transcript in place. Thus the product implementation is **sequential after transcription**, not simultaneous with ASR: https://docs.meetily.ai/features/retranscription
- Imports/retranscriptions are background jobs and may be processed serially; work submitted during live recording is queued until recording finishes. This prioritizes capture stability and gives users a Jobs tray for progress/cancel instead of unrestricted parallel inference: https://docs.meetily.ai/features/audio-import and https://docs.meetily.ai/features/retranscription

## Reusable ideas and risks

- Do not conflate diarization (“Speaker 1/2”) with biometric identification of known attendees. Upstream's historical roadmap and current beta wording support keeping naming/correction as a separate layer: https://github.com/Zackriya-Solutions/meetily/discussions/88
- Auto-running *after* recording/transcription is the safer default architecture: upstream itself recognizes a full-recording post-processing path as useful for accuracy, whereas concurrent diarization competes with live ASR for CPU and can degrade latency: https://github.com/Zackriya-Solutions/meetily/releases/tag/v0.3.0
- Upstream's whisper.cpp `--diarize` is not a general substitute for the fork's model: it assigns speaker 0/1 by comparing energy in a **stereo** file's two channels; Meetily's mic/system channels can approximate “You/Others,” but this does not cluster arbitrary people on the same channel. TinyDiarize only signals speaker turns and requires a special TDRZ model: https://github.com/Zackriya-Solutions/meetily/blob/main/backend/whisper-custom/server/server.cpp
- Several Docker configuration paths explicitly comment diarization out as “feature not available yet,” despite dormant environment/options in other files. That partial wiring is a warning against treating flags or README mentions as a working end-to-end feature: https://github.com/Zackriya-Solutions/meetily/blob/main/backend/run-docker.sh
- Upstream already has a relative CPU-allocation precedent in `llama-helper`: `available_parallelism`, then `(cores / 2) + 2`, applied to both generation and batch thread counts, with the stated goal of not starving the UI. The fork can adopt the same *relative-policy idea*, but plain half (`max(1, cores / 2)`) is more predictable when ASR and diarization might overlap: https://github.com/Zackriya-Solutions/meetily/blob/main/llama-helper/src/main.rs
- Upstream's Parakeet ONNX session builder supports explicit `intra_threads`/`inter_threads`, but the normal constructor currently passes `None`, leaving thread selection to ONNX Runtime. This is reusable plumbing, not a complete global resource policy: https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/parakeet_engine/model.rs
- Upstream already centralizes `available_parallelism()` in a cached hardware profile. A shared helper/policy is preferable to independently letting Whisper, Parakeet, Sortformer, Rayon, and llama.cpp each consume all logical CPUs: https://github.com/Zackriya-Solutions/meetily/blob/main/frontend/src-tauri/src/audio/hardware_detector.rs
- The best upstream/product precedent for auto-run is: persisted `Speaker Diarization` setting → finish/save transcript → enqueue speaker identification → expose progress/cancel in Jobs. It removes the extra click without making recording, ASR, and diarization fight concurrently: https://docs.meetily.ai/features/meeting-workspace and https://docs.meetily.ai/features/retranscription
- Because cancellation after transcript replacement is only partially atomic in the documented product, the fork should keep the hardened atomic *speaker-label replacement* behavior and clearly distinguish “transcript saved” from “diarization completed”: https://docs.meetily.ai/features/retranscription

## Conclusion

- We are **not duplicating a finished Community implementation**. Upstream Community `main` has only legacy stereo-channel/TinyDiarize support; general multi-speaker diarization and known-voice attendee matching remain absent or requested: https://github.com/Zackriya-Solutions/meetily/blob/main/backend/whisper-custom/server/server.cpp and https://github.com/Zackriya-Solutions/meetily/issues/56
- The separate Meetily product documentation shows the UX/workflow worth copying: diarization is a saved preference enabled before processing, and speaker identification automatically runs **after transcription** as a queued background stage with progress/cancellation: https://docs.meetily.ai/features/meeting-workspace and https://docs.meetily.ai/features/retranscription
- Recommendation for this fork: enable the preference by default for new installs (retain an off switch), run diarization automatically after the final transcript is saved, and avoid simultaneous live ASR + diarization. Allocate each CPU-bound local inference stage from a shared relative budget; start with `max(1, available_parallelism / 2)` threads for Sortformer and similarly cap Parakeet/Whisper where APIs allow. Upstream's own llama helper proves relative core allocation is an accepted pattern, though its `(cores / 2) + 2` formula is more aggressive: https://github.com/Zackriya-Solutions/meetily/blob/main/llama-helper/src/main.rs
- Do not replace the fork's Sortformer pipeline with upstream whisper.cpp `--diarize`: that mode only compares energy between two stereo channels and cannot cluster arbitrary participants sharing one channel: https://github.com/Zackriya-Solutions/meetily/blob/main/backend/whisper-custom/server/server.cpp
- Longer-term optional backends (MOSS/VibeVoice) may unify ASR+diarization, but upstream issues explicitly flag compute, VRAM, latency, and benchmarking concerns; they are not ready-made drop-ins today: https://github.com/Zackriya-Solutions/meetily/issues/659 and https://github.com/Zackriya-Solutions/meetily/issues/335
